# 13 – Normal-Day vs Festival-Day Traffic Simulation & SLA

Covers OBJ-02, FR-07, FR-09, NFR-01, NFR-02, NFR-07, SLA-01, SLA-02, AC-02 and AC-04.

## 13.1 Simulated user behaviour (`loadtest/locustfile.py`)

Each Locust user logs in **once** at start, using a seeded account. This avoids bcrypt dominating CPU. Users are drawn from a pool of about 70 % FREE and 30 % PREMIUM, so the queue shows a mix.

| Task | Endpoint | Weight |
|---|---|---|
| Browse menu | `GET /api/v1/menu` | 5 |
| Place order (1–4 random items) | `POST /api/v1/orders` | 3 (normal) / 4 (festival) |
| View my orders | `GET /api/v1/orders` | 2 |
| View one order | `GET /api/v1/orders/{id}` | 1 |
| Health | `GET /api/health` | 0 (ALB only) |

## 13.2 Scenarios (starting values, A-12)

| Parameter | **Normal day** | **Festival day** |
|---|---|---|
| Peak concurrent users | 25 | 250 |
| Spawn rate | 5 users/s | 10 users/s |
| Wait time between tasks | 2–5 s | 1–3 s |
| Shape | Flat for 10 min | Load shape: 0–2 min ramp to 80, 2–4 min ramp to 250, hold 4–12 min, 12–15 min ramp down to 25 |
| Duration | 10 min | 15 min (+ 15 min observation for scale-in) |
| Approx. throughput | ~7 req/s | ~120 req/s |
| Expected ASG behaviour | Stays at **2** instances (CPU < 50 %) | Scales out to **3–4** within ~3–6 min of ramp. Scales in to 2 about 15 min after load drops. |
| Expected p95 latency | < 300 ms | < 1,000 ms (brief spike during scale-out is acceptable) |
| Expected error rate | < 0.1 % | < 1 % |

**Calibration step (P8):** run a step test (25 → 50 → 100 → 150 users, 3 min each) to find the users-per-instance at which CPU reaches ~50 %. Then tune festival peak users so the ASG reaches 3–4 instances without hitting the max-4 ceiling for long.

## 13.3 Why traffic scales the fleet

- Target tracking on **ASGAverageCPUUtilization = 50 %**, with 1-minute detailed monitoring. The scale-out alarm needs 3 datapoints (~3 min). The scale-in alarm needs 15 datapoints (~15 min).
- Instance warm-up 120 s prevents over-scaling while new instances boot.
- **[OPTIONAL]** A second target-tracking policy on `ALBRequestCountPerTarget` (e.g. 60 req/target/min) can be added if CPU alone reacts too slowly.

## 13.6 SLA definition (SLA-01) — draft

> Superseded by the formal SLA in [14-sla.md](14-sla.md). Kept here for the design history.

| Element | Definition |
|---|---|
| **Service** | FeastFlow web app and API behind the ALB |
| **Availability target** | **99.5 %** per measurement period (NFR-02) |
| **Measurement period** | Calendar month, **counting only minutes when the Learner Lab session is active** (the environment can't run outside sessions) |
| **Measurement method** | A minute is **unavailable** if ALB `HealthyHostCount = 0` **or** the 5xx ratio (`HTTPCode_Target_5XX + HTTPCode_ELB_5XX`) / `RequestCount` > 5 %. Availability = 1 − unavailable minutes / measured minutes. Computed from CloudWatch 1-minute data. |
| **Latency objective** (supporting) | p95 < 1 s under festival scenario |
| **Exclusions** | Learner Lab session shutdown/start-up, AWS regional incidents, planned maintenance announced ≥ 24 h ahead, load tests deliberately exceeding the configured max capacity, client-side errors (4xx) |
| **Breach conditions** | Monthly availability < 99.5 % (≈ 3.6 h per 30-day month of measured time), **or** any single outage > 30 consecutive minutes |
| **Design measures supporting it** | Min 2 instances across 2 AZs, ELB health checks with auto-replacement, rolling instance refresh with 50 % min healthy, liveness check independent of DB |
| **Known single points of failure** | Single-AZ RDS (Multi-AZ optional), HTTP-only listener |
